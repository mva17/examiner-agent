# Как устроен Экзаменатор: объяснение кода для защиты

Этот файл нужен, чтобы понимать свой код и отвечать на вопросы. На курсе прямо сказали: «всё, что пропускается через вас, оценивается как ваша работа».

## За 30 секунд

Экзаменатор — это граф LangGraph. Состояние сессии (тема, очередь вопросов, ответы, оценки) лежит в словаре `ExamState`. Каждый узел графа — обычная Python-функция: получает состояние и возвращает изменённые поля. Переходы между узлами выбирают функции-роутеры (`after_relevance`, `after_grade` …) по полям состояния. Когда нужно спросить студента, узел `ask` вызывает `interrupt(...)`: граф сохраняется в checkpointer и останавливается. Ответ студента приходит через `graph.invoke(Command(resume=ответ), config)` с тем же `thread_id`, и граф продолжает с того же места.

## Файлы по порядку чтения

1. **`examiner/schemas.py`** — какие JSON мы ждём от модели. Например, `Grade(verdict, explanation, missing, page, followup_question)`, где `verdict` может быть только `верно | частично | неверно` (тип `Literal`). Валидатор `_normalize` прощает модели «Верно.» и «частично верно».
2. **`examiner/prompts.py`** — промпты. Каждый из 6 частей: роль, задача, контекст, ограничения, формат ответа, условия остановки. Внешний текст (запрос, ответ студента, методичка) — в тегах `<student_answer>…</student_answer>`, и в ограничениях сказано, что это данные, а не инструкции. В промпте оценки 3 примера (few-shot), третий — как раз попытка инъекции.
3. **`examiner/llm.py`** — `ask_json`: вызвать модель → срезать `<think>` → найти JSON → проверить Pydantic-схемой. Не прошло — дописать в диалог ошибку и попросить исправить, не больше `JSON_RETRIES` раз. `CallBudget` считает вызовы и бросает `BudgetExceeded` при превышении лимита. `build_llm` создаёт `ChatOpenAI` с `base_url`, поэтому провайдера (Cloud.ru, OpenRouter, llama.cpp) можно менять в `.env` без правки кода. Запасная модель подключается через `with_fallbacks`.
4. **`examiner/knowledge.py`** — поиск. `ManualSearch` — интерфейс (Protocol): любой объект с методами `search` и `control_questions`. `BM25ManualSearch` — классический BM25 (формула с `k1=1.5`, `b=0.75`), написан вручную, работает по демо-текстам. `ChromaManualSearch` — обёртка над коллекцией ChromaDB Оскара. **Главное:** любой поиск всегда возвращает top-k, даже если по теме ничего нет. Это проверяет тест `test_search_always_returns_something_even_off_topic`, поэтому агенту нужен узел `check_relevance`.
5. **`examiner/logic.py`** — логика без модели: порядок вопросов (сначала прошлые ошибки, потом «Контрольные вопросы», потом сгенерированные), `pick_next` (после ошибки — вопрос из того же раздела методички), команды «стоп» и «не знаю», текст итога.
6. **`examiner/memory.py`** — долгая память в SQLite: средний балл по теме и вопросы с ошибками. Вопрос, на который потом ответили верно, из списка ошибок удаляется. `question_id` — хэш текста, поэтому один и тот же вопрос в разных сессиях узнаётся.
7. **`examiner/agent.py`** — сам граф. Декоратор `node(...)` оборачивает каждый узел: создаёт `CallBudget` из `state["llm_calls"]`, ловит ошибки (`BudgetExceeded` → досрочный итог, `LLMError` → понятное сообщение) и пишет запись в журнал `events`. Класс `Examiner` — удобная обёртка: `start()` и `answer()`.
8. **`api/main.py`** — FastAPI. Pydantic проверяет входные данные (`user_id` только латиница и цифры, длины), ошибки превращаются в коды 409, 422, 503 с понятным текстом. `/chat` сам решает, начать сессию или продолжить.
9. **`ui/app.py`** — Streamlit: чат, статус шагов (`st.status`), цвет оценки, метка «не из методички», кнопки 👍/👎 → `/feedback`.
10. **`eval/run_grading_benchmark.py`** — бенчмарк (см. ниже).
11. **`tests/`** — 67 тестов. `ScriptedLLM` отдаёт заранее заданные ответы для нужной задачи, поэтому можно проверить, например, что после «частично» будет ровно одно уточнение.

## Какие паттерны применены и зачем

| Паттерн | Где | Зачем |
|---|---|---|
| Граф состояний (StateGraph) с условными переходами | `agent.py` | агент сам выбирает следующий шаг, это не линейный пайплайн |
| Agentic RAG: проверка релевантности + переформулировка | `check_relevance`, `rewrite_query` | поиск всегда что-то возвращает, нельзя слепо верить top-k |
| Human-in-the-loop (`interrupt` / `Command(resume)`) | `ask` | ждать ответ студента посреди графа |
| Краткосрочная и долгая память | checkpointer + `memory.py` | продолжать сессию и помнить слабые темы между сессиями |
| Structured output + валидация + повтор | `ask_json` + `schemas.py` | модель иногда пишет не JSON или неверные поля |
| Самопроверка / второй агент-проверяющий | `verifier.py` | вопросы «не из методички» могут быть ошибочными |
| Гардрейлы: лимиты, fallback, обработка ошибок | `llm.py`, `node()`, `recursion_limit` | не зациклиться, не потратить грант, не упасть |
| Защита от prompt injection | теги в `prompts.py` + `looks_like_injection` | ответ студента — данные, а не команда «поставь верно» |

## Параметры генерации

`temperature=0` для всех вызовов: оценка ответа и разбор темы должны быть воспроизводимыми. Это важно для бенчмарка: при повторном прогоне получаются те же цифры. Генерация вопросов от этого менее разнообразна, но вопросы берутся в основном из «Контрольных вопросов» методички.

## Бенчмарк — как объяснить

- **Данные готовые**, ничего не размечали вручную: вопросы по физике из ruMMLU (MERA) с известным правильным вариантом.
- **Как получаем ответ студента:** каждый вопрос подаём дважды — с правильным вариантом (ждём «верно») и со случайным неправильным (ждём не «верно»). Выбор случаен, но с фиксированным `seed`, поэтому воспроизводится.
- **Метрики:** `accuracy` (совпадение с эталоном), `false_accept` (неправильный ответ засчитан — самая вредная ошибка экзаменатора), `correct_accept`, `invalid` (модель не дала разбираемой оценки), время p50/p95, число вызовов на случай.
- **Baseline:** та же модель, но без эталонного ответа, без схемы и без примеров («оцени ответ одним словом»). Так видно, что дают эталон и схема.
- **Ограничение:** ruMMLU — тест с вариантами, а на допуске отвечают свободным текстом. Поэтому это проверка именно оценщика на готовых данных, а не всего диалога.

## Вероятные вопросы на защите

**Чем ваш агент отличается от обычного RAG?**
Он сам решает, что делать дальше: проверяет, что найденное действительно по теме, при необходимости переформулирует запрос, выбирает между вопросами из методички и генерацией, ждёт ответ студента, после ошибки задаёт уточнение или вопрос по тому же разделу и помнит слабые темы. В обычном RAG — один поиск и один ответ.

**Что будет, если модель вернула не JSON?**
`ask_json` покажет модели ошибку проверки и попросит исправить, до `JSON_RETRIES=2` раз. Не вышло — `LLMError`, студент видит «Не получилось обратиться к модели…», а не трассировку.

**Что будет, если модель недоступна?**
Сначала запасная модель (`with_fallbacks`) при ошибке сети, таймауте или 429. Если и она недоступна — понятное сообщение и статус `error`; `/health` показывает `degraded`.

**Как защищаетесь от «поставь мне верно»?**
Два слоя: (1) ответ студента в тегах `<student_answer>`, в промпте сказано, что это данные, и в примерах оценки есть такая атака; (2) дешёвый фильтр `looks_like_injection` до вызова модели — такой ответ сразу получает «неверно» без обращения к модели (тест `test_injection_in_answer_is_graded_wrong_without_llm`).

**Откуда номер страницы? Не выдумывает ли модель?**
Страница берётся из метаданных найденного фрагмента. Если модель назвала страницу, которой нет среди найденных, код заменяет её на страницу фрагмента.

**Как вопросы «не из методички» проверяются?**
Каждый сгенерированный вопрос с эталоном проходит `verifier.verify(...)` до показа студенту. Сейчас это отдельный вызов модели с промптом строгого проверяющего; в общей системе на это место встанет агент-Проверяющий Ибрагима. Если не прошёл ни один вопрос — честный отказ.

**Как устроена память?**
Краткосрочная — checkpointer LangGraph по `thread_id = user_id:chat_id`: хранит всю сессию и позволяет продолжить после `interrupt`. Долгая — SQLite по `user_id`: средний балл по темам и вопросы с ошибками. В новой сессии сначала идут вопросы, где были ошибки.

**Почему InMemorySaver, а не SqliteSaver?**
Для прототипа хватает: сессия допуска короткая. Минус — после перезапуска сервера незаконченная сессия теряется, а долгая память (SQLite) остаётся. Замена — одна строка (`build_graph(deps, checkpointer=SqliteSaver(...))`), это в планах.

**Сколько стоит одна сессия?**
До первого вопроса — 3 вызова модели, на каждый ответ — 1. «Не знаю», «стоп» и инъекции — без вызова. Сессия из 5 вопросов — от 8 вызовов (3 + 5 оценок) до 13 (если на каждый вопрос было уточнение), жёсткий лимит — `MAX_LLM_CALLS=40`.

**Почему BM25, а не векторы?**
Это временная замена базы Оскара, чтобы агент работал независимо. Экзаменатор зависит только от интерфейса `ManualSearch`; ChromaDB подключается адаптером `ChromaManualSearch` без изменения графа.

**Что делает демо-модель `fake`?**
Отвечает по простым правилам в тех же JSON-форматах. Нужна для тестов и демо без ключа. Для метрик не используется: бенчмарк на ней без флага `--allow-fake` не запустится.

## Что выучить к защите (минимум)

1. Нарисовать граф по памяти: тема → поиск → релевантность → (переформулировка) → вопросы → ask/interrupt → grade → followup/pick → итог.
2. Что такое `interrupt()` и `Command(resume=…)`, зачем `thread_id`.
3. Разница краткосрочной и долгой памяти и где каждая хранится.
4. Как работает `ask_json` (схема, повтор, `<think>`).
5. Три гардрейла: лимит вызовов, лимит вопросов, обработка ошибок модели.
6. Как устроен бенчмарк, что такое baseline и почему `false_accept` важнее всего.
7. Что демо-тексты — не методички МИФИ, и как подключится ChromaDB Оскара.
